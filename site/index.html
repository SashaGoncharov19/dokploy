What it does

A control panel for your own servers

Point it at a machine you rent or own. It builds from Git, runs the containers, hands out TLS certificates and keeps the backups — the parts of a PaaS you would otherwise rent by the month.

✓
Applications in any languageNode, PHP, Python, Go, Ruby, Rust — built from a Dockerfile, Nixpacks or buildpacks.

Getting started

From nothing to a deployed app

Assuming a fresh Linux box with Docker on it.

1

Run the installer

It initialises Docker Swarm, starts PostgreSQL and Traefik, and brings the panel up on port 3000. Nothing else on the host is touched.

2

Open it and create the first account

Visit http://your-server-ip:3000. The first account registered becomes the owner; registration closes behind it.

3

Create a project and deploy

Connect a Git provider or paste a repository URL, pick a build method, add a domain. The first deploy usually takes a couple of minutes while the image builds.

Benchmarks

What changing the runtime actually did

Head-to-head against a build of the pre-migration commit. Same host, same PostgreSQL, byte-identical rendered output. Medians over repeated runs, and the harness is committed so the numbers can be re-run rather than believed.

MetricNodeBunChange
Shutdown — docker stop to exited3019 ms318 ms9.5× faster
Memory, under load1315 MiB760 MiB−42%
Runtime image3.22 GB1.96 GB−39%
Cold boot, incl. 186 migrations4720 ms3411 ms1.4× faster
Dependency install, warm cache21.9 s5.5 s4× faster
API service image1.25 GB234 MB5.3× smaller
SSR throughput780 rps745 rpsno change

Throughput did not improve. Both request benchmarks land inside noise, with the Node baseline nominally ahead. The request path is bounded by Next.js and React rendering, not by the engine underneath — so swapping the engine does not move it. Anyone promising a faster dashboard from a runtime swap is selling something. What moved is startup, shutdown and memory, and the shutdown figure is the one you feel: the service runs stop-first, so every update waits on it.

Differences

How it differs from upstream

Every feature unlocked

No licence key, and nothing contacts a licensing API. Whitelabeling, SSO, SCIM, custom roles, audit logs and forward-auth all work out of the box.

Bun-native internals

node-pty → Bun.Terminal, bcrypt → Bun.password, postgres.js → Bun.sql. Existing password hashes keep working in both directions.

Its own registry

Update checks point at this fork's images, so pressing Update can never quietly replace your build with an upstream Node one.

Still merges upstream

Divergence is kept deliberately narrow so Dokploy's fixes keep flowing in. The last upstream merge — 45 commits — landed with zero conflicts.

Channels

Two ways to track it

Pick the one that matches how much churn you want.

:latest

Stable. Moves only on a tagged release. This is what the installer picks by default, and what the update button offers.

:canary

Pre-release. Published on every merge. Useful for trying fixes early — expect it to move under you.

Switching stable → canary is safe. Going back is not. Database migrations only run forward, so once canary has applied newer ones, a stable image that does not know about them cannot start cleanly against that database.

Questions

The things worth asking about a fork

Why would I run a fork instead of Dokploy itself?

Two reasons, and neither is "it is faster at serving pages" — it is not. First, every enterprise feature is unlocked, so whitelabeling, SSO, SCIM, custom roles and audit logs work without a licence key. Second, the runtime differences that are real: shutdown is 9.5× quicker, which you feel on every update, and the image is 39% smaller. If neither matters to you, upstream Dokploy is an excellent choice and you should use it.

Is it kept up to date with upstream?

Yes, and deliberately so. Divergence is kept narrow specifically to keep merges cheap — the last upstream merge brought in 45 commits and landed with zero conflicts. That is the whole reason this fork refuses to reformat files it is not otherwise changing.

Can I migrate an existing Dokploy install to this?

Yes — it is the same database schema, so pointing this image at your existing volume works. One migration matters: 0186 backfills server assignments before the enterprise gates open, because unlocking them narrows visibility from every organisation server to only assigned ones. Without the backfill your member-role users would open the dashboard to an empty list. It is idempotent and verified against real PostgreSQL.

Can I go back to upstream if I change my mind?

Yes. Password hashes are compatible in both directions, and the two licence columns are deliberately still in the schema so an upstream image can read the database. That is why they have not been dropped yet.

How do I know the benchmark numbers are real?

Because the harness that produced them is committed — scripts/runtime-benchmark.ts builds its own PostgreSQL and containers, runs every phase and tears it down. The write-up also records the measurements that failed: a Turbopack build that was 4.7× faster and rejected for making the bundle larger, a config change that did nothing, and a first benchmark pass whose conclusion turned out to be wrong.

Who maintains it?

One person, in the open. That is worth knowing before you put production on it. The upstream project it tracks is considerably larger and better resourced, and everything the product does comes from there.

Upgrading

Coming from an unlicensed Dokploy

One migration deserves a read before you run it.

0186

Unlocking the enterprise gates flips server visibility from every organisation server to only assigned servers. This migration backfills the assignments first, so a member-role user sees exactly what they saw before. Without it, they would open the dashboard to nothing.
